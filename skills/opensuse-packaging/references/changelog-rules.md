# Changelog (`*.changes`) — format and content rules

Owner of: what an entry may and may not say — bullet levels, curation, the no-URL rule, the
never-alter-a-previous-entry HARD RULE and its sanctioned exceptions, literal patch naming, CVE
ids, and how much to write. The *mechanics* (template, timestamp, author line, the prepend itself,
the `changes-*.sh` scripts) are `references/changelog-entry.md` — cross-linked, deliberately not
merged.

## Changelog (`*.changes`)

https://en.opensuse.org/openSUSE:Creating_a_changes_file_(RPM)

### Format and layout

- openSUSE keeps the changelog in a separate `<name>.changes` file, not inside `%changelog` in the spec.
- Use `osc vc` to add a new entry — it stamps the date/email correctly.
- Newest entry at the top. Entries are separated by a line of 67 dashes. Wrap text at 67 columns.
- **First-level bullet `-`, second-level `*`. No third level.** The `/usr/lib/build/changelog2spec` helper specifically recognizes these two symbols for auto-reindenting, and yast2-qt renders deeper levels badly — so never use a third level. **Every item is a bullet** — never write a `.changes` entry body as a bare prose paragraph; a single note still gets a leading `- `, and continuation lines wrap indented under their bullet.
- **Group related changes thematically.** Related changes go under one first-level `-` bullet with second-level `*` sub-bullets; don't pad with implementation detail. When amending the session's entry with a later change, nest it as an additional `*` under an existing top-level dash if it fits thematically (e.g. another guideline-refresh tweak); otherwise add a new top-level `-`.
- Reference bugs as `bsc#NNNNNN` (SUSE bugzilla) or `boo#NNNNNN` (openSUSE). Avoid `bnc#`.

### Curate the entry — never dump a raw log, never substitute a URL

- **HARD RULE: condense and curate an auto-generated changelog before committing — never ship the raw commit/PR firehose.** `changesgenerate` (and pasted upstream release notes) dump every commit; that list is for *humans reading the package changelog*, not a git mirror. **Drop entirely:** CI / GitHub-Actions / `.github` / devcontainer / release-tooling changes; non-Linux platform changes (Windows, macOS/darwin, mingw, BSD-only); test-only changes; routine dependency-bump noise (`chore(deps): bump …`, dependabot — collapse to at most one "updated vendored dependencies" line, or drop); pure refactors / lint / formatting / typo-in-comment churn. **Keep:** new features, behaviour changes, bug fixes, security/CVE fixes, removed/renamed commands, deps that affect packaging. Plain readable bullets beat raw `feat(x):`/`fix(y):` conventional-commit prefixes unless the prefix aids clarity. (Real miss: gh 2.95.0 shipped the raw list incl. "Bump Go in devcontainer" and several `chore(deps)` bumps.)
- **HARD RULE — never substitute a URL for the changelog content.** A `.changes` entry must not point at a release-notes page (or any other link) *in place of* describing the change — no "see https://…/releases/ for the full notes", no "full changelog: <url>". A bare link is not an audit trail: it rots, and it forces every reviewer and future maintainer to leave the changelog to find out what actually changed. Instead, read the upstream release notes and **distil a concrete, Linux/openSUSE-user-relevant summary** as bullets — what changed for someone running or packaging the software on openSUSE: new features, behaviour changes, bug/security fixes, new/removed dependencies or plugins — across *all* the versions you skipped. Curate it exactly like the condense rule above (drop CI/non-Linux/test-only/dep-noise). A URL may appear only as *supplementary* context after a real summary, never as a replacement for it. (A plain `Version X.Y` with no body, or a body that is just a link, is the failure mode this forbids.) The one sanctioned closer: a URL-free sub-bullet saying the list is abridged, *after* a real summary — see the ~20-line ceiling under the summarise-every-bump rule below.

### Never alter a previous entry — HARD RULE, and the sanctioned exceptions

- **HARD RULE — never alter, reword, reformat, re-indent, or absorb a previous `.changes` entry.** When adding a new entry, insert it cleanly at the top and leave every existing entry — its `---` separator, `date - author` header, and body — **byte-for-byte intact**. The classic self-inflicted bug: an Edit whose anchor is the top separator + the next entry's header *replaces* that header, so the old entry's bullets silently re-attribute to your new entry. Avoid it by re-including the next header **verbatim** in the replacement, or by prepending your whole block (ending in a blank line + `---`) ahead of the first separator. **Always show the changelog diff before committing** to catch a mangled neighbour. The sanctioned edits of an old entry are exactly two — adding a `boo#`/CVE reference to a previously-released one (and for an already-Factory package, that also needs a fresh entry to carry the SR), and repairing a header the **source validator itself rejects** (below); amending the still-in-flight, not-yet-released entry of an under-review update is likewise fine.
  - **Sanctioned exception 2 — a header `check_dates_in_changes` refuses.** Rare but real, and there is no way around it: factory-auto declines the submission with `ERROR: INVALID DATE "<str>" (<pkg>.changes:<line>)`, and the file cannot reach Factory in *any* form until that header parses — so the entry must be edited even if it is decades old and someone else's, and even if the same broken line is already sitting in Factory (it usually is; the validator got stricter over time). the maintainer confirmed 2026-08-07: *"this is rare case when its acceptable to change changelog of package that is in factory - its a rare exception but existing one we have to work with it"*.
    - **Understand the parser before editing, because the fix is usually one separator, not a rewrite.** `/usr/lib/obs/service/source_validators/helpers/check_dates_in_changes` accumulates the header's whitespace-separated tokens into `DATESTR` and **breaks at the first token containing `-` or `@`**, then runs `date -d "$DATESTR"`. So a header missing the canonical ` - ` before the author swallows the *name* into the date and fails. Restoring just ` - ` makes `DATESTR` the bare date and it parses — **do not invent a time or reflow the line**. (Real case: `hardware:sdr/svxlink`, `Sat Apr 14 2007 Tobias Blomberg (SM0SVX) <…>` → `Sat Apr 14 2007 - Tobias Blomberg (SM0SVX) <…>`, one line, SR 1370142.)
    - **Do not trust the remedy the decline suggests.** It points at `helpers/fix_changelog`, which pipes the file through `helpers/changelogfilter`; on that svxlink file it was a **no-op** (zero-line diff). Always dry-run it on a copy first, and hand-fix when it does nothing.
    - **Prove it on a copy before touching the real file:** `cp` the `.changes` aside, apply the one-token fix, and run `check_dates_in_changes <copy>` directly — exit 0 is the confirmation. Then scan *every* header so one submission fixes them all instead of ping-ponging with factory-auto: `awk '/^-------/{getline; if ($0 !~ /^[A-Z][a-z][a-z] [A-Z][a-z][a-z] [ 0-9][0-9] [0-9][0-9]:[0-9][0-9]:[0-9][0-9] [A-Z]+ [0-9]{4} - .+ <.+>$/) print NR": "$0}' <pkg>.changes`. Note most hits are only bare-email author lines with *valid* dates — the validator tolerates those, and they are **not** yours to rewrite; fix only what it actually rejects.
    - **`changes-guard.sh` will refuse this (exit 1) and that is correct** — it enforces insertion-only. Override it only with the evidence recorded: the diff touches nothing but the offending header, the separator count is unchanged (`grep -c '^----'`, before == after), and a bullet on your own new/in-flight entry states which header was repaired and why. Say so in the SR message too, so the reviewer is not surprised by a diff below the top entry.
  - **The in-flight amendment exception, spelled out with real cases:** the top entry describing an update whose SR is still `new`/`review` (not yet *accepted* into Factory) has not reached the official repo yet, so reviewer-feedback fixes to that same in-flight change fold into that existing entry rather than stacking a new one. (Real case: a reviewer asked to drop a bogus `Provides:` on the in-flight bitcoin 31.0 SR — the fix folded into the existing 31.0 entry, no new entry.) **HARD constraint: only amend an entry *you yourself* authored.** If the top in-flight entry was written by a *different* packager, never fold your change into it — prepend a fresh entry under your own author line (editing someone else's entry rewrites their authored history and misattributes your change). Check the author line first. (Real case: jsoncpp i586 FTBFS fix — the top entry was another maintainer's "Switch back to meson build", so the `-fexcess-precision=standard` fix went into a new entry, not theirs.)

### Name every added or removed patch literally

- **HARD RULE — name every added or removed patch (by filename) in the `.changes`.** Factory's `factory-auto`/`check_source` review **auto-declines** the SR otherwise, one line per unmentioned patch: *"A patch (foo.patch) is being added/removed without this addition/removal being mentioned in the changelog."* A summary like "replace the old patches with the distro set" does **not** satisfy it. Write `- Add foo-fix.patch: <what>` / `- Drop bar.patch: <why — merged upstream / obsolete>`; for a big patch-set swap, enumerate every added and every removed filename. Applies to git-workflow PRs too (keep the changelog consistent). (Real case: the xar mackyle→Apple lineage switch was declined for 3 removed + 9 added patches named only collectively.) **The bot's match is mechanical — a literal substring of one `+`/`-` line of the `.changes` diff against the SR *target*** (`check_source.py`, `detect_mentioned_patches`): a glob (`foo-*.patch`), a `%{version}` form, a rename described by one name, or a filename broken by the 67-column wrap all decline even though a human reads them fine; a rename is a removal *and* an addition, so name both. A mention in an untouched older entry does not count, and in a branched checkout your own last commit is not the bot's baseline — the target is. The local `osc service run source_validator` does **not** run this cross-check, so without a local gate you meet it as a server-side decline; `scripts/changes-patches.sh` runs the identical rule locally and is part of the commit gate. Remediate a decline of this kind by amending the in-flight entry with the literal names and `osc sr … --supersede <declined-id>` (revoke-then-fresh-`sr` when the sources must change too — `references/submit-watch.md` "Triaging your declined submit requests"). (Real case: a three-patch rename `zoo-2.10-*.patch` → `zoo-2.10.1-*.patch` took three SRs — first a glob, then the added side still a glob.)

### CVEs and security bullets

- **HARD RULE — CVEs need full identifiers.** Any mention of fixed security issues MUST cite the literal `CVE-XXXX-NNNN` id(s), one per fix (ideally paired with a `bsc#`/`boo#`). A vague "fixes multiple CVEs" / "security hardening (CVEs)" bullet without the actual IDs is unacceptable — the SUSE/openSUSE security tracker keys off the literal CVE strings.
- **PREFERRED LAYOUT for a security-fix bullet — CVE id first, bug ref last, patch as a sub-bullet.** One top-level `-` bullet per CVE, opening with the bare id and a colon, then what the vulnerability actually *is* (component + impact, not "security fix"), then the `bsc#`/`boo#` in parentheses at the end; the patch that fixes it goes on a `*` sub-bullet as a bare filename. Wrap at 67 cols, continuation lines indented under the text:
  ```
  - CVE-2026-54886: SSH SFTP server denial of service via extended
    channel data infinite loop (bsc#1270246)
    * fix-CVE-2026-54886.patch
  - CVE-2026-48860: Erlang/OTP ssl (inet_tls_dist module) allows
    unauthenticated bypass of the distribution-over-TLS LAN allowlist
    (bsc#1268146)
    * fix-CVE-2026-48860.patch
  ```
  the maintainer's stated preference, 2026-08-09. It satisfies three separate rules at once — the literal CVE id for the security tracker, the `bsc#` cross-reference, and the name-every-patch rule that `factory-auto` declines on — so use it whenever a patch lands *because of* a CVE. One CVE per bullet even when a single patch fixes several (repeat the patch sub-bullet), and never merge two CVEs into one bullet. For CVEs fixed by a *version bump* rather than a patch there is no patch sub-bullet: keep the `CVE-…: description (bsc#…)` shape as sub-bullets under the update dash. For CVEs the package is *not* affected by, use the state-not-authorship form in the rule further down instead.
- **HARD RULE — proactively search upstream for CVE IDs on every version bump.** Don't wait for release notes to spell them out; mine the commit range yourself. Clone/fetch upstream and grep between the old and new tag:
  ```
  git clone --filter=blob:none <upstream-url> /tmp/x && cd /tmp/x
  git log <oldtag>..<newtag> --pretty='%s%n%b' | grep -ioE 'CVE-[0-9]{4}-[0-9]{4,7}' | tr a-z A-Z | sort -uV
  ```
  Also scan the GitHub release page and any `SECURITY`/`NEWS`/`ChangeLog` file. For each ID: (1) confirm it's a *fix* by mapping it to its commit subject (`git log <range> -i --grep=<cve> --pretty=%s`), and (2) confirm it isn't already credited in an earlier `.changes` entry (`grep -ioE 'CVE-[0-9]{4}-[0-9]{4,7}' <pkg>.changes`). List every genuinely-new ID in the update entry, wrapped at 67 cols. Only when a thorough search yields nothing concrete do you fall back to a factual, non-CVE description (e.g. "many crash and memory bugs fixed via OSS-Fuzz") — never claim CVEs you can't name.
- **HARD RULE — when a package has open CVE bugs it is NOT affected by, record that in the `.changes` with the evidence.** The bug sweep of SKILL.md item 7 regularly turns up open `VUL-` bugs whose vulnerable component already sits above its fix floor in what you ship — a vendored crate lifted by an earlier re-vendor, or a version the package never carried. Staying silent has a real cost: the next sweep re-investigates from scratch, and the security team has nothing to close on. Record each as a sub-bullet under the dependency-refresh dash, naming the CVE, the `boo#`, the shipped version and the floor: `* CVE-2025-55159 (boo#1248048): slab is 0.4.12, above the 0.4.11 fix`. Four constraints: **verify the floor** from the advisory itself (RUSTSEC / GHSA `patched`) and the **actually-shipped** version from the vendor/registry tarball — *not* the upstream lockfile, which a `cargo_vendor` run with updates enabled will differ from; **grep the whole `.changes` first and skip any CVE already cited** in an earlier entry; **never write the line for a CVE with no published fixed version** — say nothing rather than imply a fix (real: CVE-2024-43785's GHSA carries `patched: None`, so gitoxide's changelog stays silent and the bug went back to the user as unresolved); and phrase it as **state, not authorship** — "is not affected by", never "fixes". maintainer feedback, 2026-08-08: *"as those are already fixed mention them in changelog as already resolved (if they were not mentioned already)"*.
  - **This is the third sanctioned reason to amend an already-committed, in-flight entry**, alongside reviewer feedback and the header repair above. When the sweep surfaces the bugs only *after* you committed and filed the SR, fold the not-affected block into your own existing top entry via `changes-guard.sh --amend-top '<Name> <email>'`, refresh the header timestamp, and **supersede** the request (`osc sr <prj> <pkg> openSUSE:Factory -s <old-id>`) instead of stacking a second entry. maintainer feedback, 2026-08-08: *"in this case ammending changelog is also ok — its one of rare exceptions"*. (Real case: gitoxide 0.56.0, SR 1370351 already in review when boo#1236139 turned out to be long fixed by gix-worktree-state 0.33.0 against a 0.17.0 floor.)

### How much to write — upstream bumps vs packaging-only changes

- **HARD RULE — every version bump summarises the actual upstream changes as bullets, including small point releases.** Read the release notes / `CHANGELOG` / `NEWS` (or mine the commit range) for *every* version you cross and list the user-facing items — new features, behaviour/API changes, bug and security fixes, new/removed deps or plugins — curated per the condense rule (drop CI/non-Linux/test-only/dep-bump noise). **This is not reserved for big releases:** a two-line patch release still earns its one or two substantive bullets. A bare `- Update to X.Y.Z` with no body is a defect *unless* the release genuinely has nothing consumer-relevant — and then say so explicitly (e.g. `* No user-visible changes`). Summarise for an openSUSE *user*; don't dump the full release notes and don't reference the changelog by URL alone (see the no-URL rule). Rule of thumb: ~10–15 lines on a big release (**~20 is the ceiling** for an upstream version bump; the packaging-only rule below is stricter), a couple of concrete bullets on a point release, never zero. When even the curated list would run past ~20 lines, trim in this order until it fits — feature detail first, then minor bug fixes — keeping the behaviour/packaging changes, and **never cutting a security fix: every one stays, each with its full `CVE-` id**. Close the abridged entry with one URL-free sub-bullet (`* Many more fixes and improvements; see upstream's release notes for the full list`) so a reader knows there is more; that is the sanctioned exception to the no-URL rule above, because it follows a real summary. Start from the release body when the project publishes one (`curl -sS https://api.github.com/repos/<o>/<r>/releases/tags/<tag> | jq -r .body` or `gh api repos/<o>/<r>/releases/tags/<tag> --jq .body`) — it is usually upstream's own curated highlights and a better source than a raw `CHANGELOG` or commit mining. (Real miss: several point-release bumps — e.g. langsmith 0.10.9, python-uv 0.11.31 — were first written as a bare `- Update to X.Y.Z` even though upstream listed concrete bug fixes worth recording.)
- **When upstream ships no `NEWS`/`ChangeLog`/release-notes (common for libraries that just track another project's release train, e.g. swift-corelibs-libdispatch), mine the commit range and filter to packaging-relevant subjects.** Pull the range with the compare API (`curl -sS "https://api.github.com/repos/<o>/<r>/compare/<oldtag>...<newtag>" | jq -r '.commits[].commit.message'` or `gh api ... --jq ...`), then grep the subject lines for the categories a packager/user cares about — new platform/libc support (`Musl`, `FreeBSD`, `Android`), arch (`riscv`, `ARM64`), build-system (`CMake`, `install dirs`, `build id`), and notable fixes — and turn those into a handful of concrete bullets. This yields a verbose-yet-honest entry without inventing anything and surfaces the same spec-affecting items the up-front change-extraction rule wants. (Real case: libdispatch 5.6.3→6.1.1 had no NEWS file; the 90-commit compare yielded Musl support, Linux build IDs, un-hardcoded CMake install dirs, Android `posix_memalign` fallback, and Windows fixes.)
- **HARD RULE — when the obvious changelog source is opaque, dig one level deeper before settling for a vague entry. Be aggressive about finding the real changes.** An uninformative *subject* line does not mean there is nothing to report, and "no upstream changelog" is a conclusion to reach only after actually looking. Escalate in this order, stopping at the first that yields substance: (1) the release notes / `NEWS` / `CHANGELOG`; (2) commit **subjects** over the range; (3) **commit message bodies** — squash-merge and monorepo-export workflows routinely put a one-line subject on top of a full itemised change list; (4) trailers pointing elsewhere (`Source-Revision:`, `Upstream-Commit:`, `X-monorepo-ref:`) and the repo/tag they name; (5) the diff itself for user-visible surface (new/removed CLI flags, config keys, installed files, dependency edits). **The specific trap:** repos that mirror a private monorepo emit every commit with an identical, meaningless subject — `Synced from monorepo`, `Sync`, `Export from internal`, `Update from upstream` — so a subject-only scan (the rule above) returns N copies of one useless string and looks like "no changes to report", while each body holds twenty-plus real entries. Always print the *full* message, not just the first line: `gh api repos/<o>/<r>/compare/<old>...<new> --jq '.commits[].commit.message'` (or the equivalent `curl`+`jq`) already returns whole messages — don't pipe them through `head -1`/`--jq '.commits[].commit.message | split("\n")[0]'`. Then condense the union of those bodies into thematic bullets per the condense rule. (Real case: a pinned-snapshot agent CLI whose eight commits were all subject-lined `Synced from monorepo` — the bodies together carried ~150 itemised changes including three explicit security fixes, which a subject-only pass would have shipped as "periodic sync from upstream".)
- **A round of spec cleanup still earns one brief umbrella bullet — don't suppress the changelog entirely.** The "no consumer-visible delta → no bullet" cases (see SKILL.md ".changes records net change") are about not *padding*, not a licence to commit a visibly-changed spec with an empty `.changes`. When you modernise/tidy a spec (spec-cleaner pass, macro conversions, dropping cruft, `%files` hygiene), add **one brief umbrella bullet** — e.g. `- Spec cleanup` with a couple of short sub-bullets, or a one-liner like `- Modernize spec file`. This is the norm reviewers expect; a commit that visibly changes the spec but carries no `.changes` line looks like an oversight. Keep it terse (don't enumerate whitespace); genuinely consumer-visible changes in the same session (version bump, dropped/added deps, a dropped `Provides`/`Obsoletes`) still get their own explicit bullets alongside the cleanup umbrella.
- **HARD RULE — the verbosity rules above are for *upstream* changes on a version bump. A packaging-only change gets a SHORT entry: one bullet per change, and the reasoning goes in the SR message, not the `.changes`.** The "summarise every version", "~10–15 lines, ~20 the ceiling", "dig one level deeper", "be aggressive about finding the real changes" rules all exist because *upstream's* changes are hard to discover and the packager is the only one who will do it. None of that applies when the version is unchanged and you fixed an FTBFS, enabled a `%check`, corrected a `License`, or restructured `%files` — there you already know exactly what changed, and the temptation runs the other way: to write up the *investigation*. Don't. Concretely, for a no-version-bump change:
  - **One bullet per change a reader can act on**, each ~1–3 wrapped lines. Say **what changed and its consequence**, not how you found it: *what* was broken, *what* you did, and a `boo#`/CVE ref if there is one.
  - **Cut the evidence, the measurements, and the disproved hypotheses.** The alternative fix you ruled out, the mechanism you traced, the sentinel value that proved it, the exact pass/skip counts, the cost/benefit of a restructure — all of that is genuinely valuable and belongs in the **SR description**, where the reviewer reads it once while deciding. The `.changes` is permanent and every future maintainer scrolls past it forever. **Same facts, two audiences, two lengths** — write the long version in the SR message first, then distil the bullets from it.
  - **The test for a line:** would a maintainer years from now, skimming to answer *"when and why did this change?"*, need it? "Fixed the aarch64 build: lld20 ships no unversioned `/usr/bin/ld.lld`, so select the version-matched linker via a custom CMake linker type (boo#1193892)" passes. A paragraph on why overriding `CMAKE_<LANG>_USING_LINKER_LLD` doesn't work does not — that is SR-message material.
  - Restructures that ship **byte-identical RPMs** (a `_multibuild` split, moving a section) still earn their bullet — the *next* packager needs to know the layout changed — but one bullet, not a rationale.
  - (Real case: the zig0.15/zig0.16 aarch64 + `%check` + licence work was first written as ~50–60-line entries carrying the cmake-shadowing mechanism and per-arch test counts; condensed to ~20 lines of plain bullets, with every dropped detail preserved in the SR description. maintainer feedback, 2026-08-14: *"for zig changelog entries they should be shorter — condensate them"*.)
- **Don't credit bundled-component bumps the package doesn't use.** If the spec builds against the system copy of a library (e.g. `-DOPENBABEL_USE_SYSTEM_INCHI=ON` with `BuildRequires: inchi-devel`), omit upstream's "bundled X updated to N" note from the `.changes` — it's misleading because that bundled copy isn't shipped.

### Every submit request carries an entry

- **A new submit request must carry a `.changes` entry — effectively mandatory.** Any SR that *introduces a change* to the target (a version bump, a new package's initial packaging, a spec change) needs a matching `.changes` entry; reviewers and the Factory tooling expect every content-changing SR to be accompanied by a changelog bullet, and a new package's first SR needs an `- Initial package …` entry. The **only** real exception is a pure *resubmit of unchanged content* — e.g. re-filing an SR that was declined for a transient/infra reason with byte-identical sources — where there is genuinely nothing new to record. If you also did cleanup as part of such a resubmit, that cleanup still earns its brief umbrella bullet (per above), so in practice almost every SR you file should touch `.changes`.
- `scripts/changes-prepend.sh` mechanizes the prepend + separator-count verification (see the prepend-is-insertion HARD RULE in SKILL.md "Adding a .changes entry").
