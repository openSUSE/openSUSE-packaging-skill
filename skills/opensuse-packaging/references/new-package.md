# Creating a brand-new package

Owner of: the from-scratch checklist (harvest, copypac-vs-port, the distros-disagree tiebreak) and the
submit route for a package Factory does not have yet. Spec rules themselves stay in
`references/specfile-guidelines.md`; the build loop in `references/update-build.md`.

## New package from scratch

**When creating a BRAND-NEW package, survey other distros for the *packaging itself* before writing a line of spec — HARD RULE.** This is distinct from the fix-survey hard rule (Core directive item 8, which surveys for *fixes* when touching an existing package): here you are surveying for the *packaging structure* of something Factory does not have yet. Before authoring the spec, look at how Fedora, Debian, Gentoo, Arch, Alpine, openEuler, Void, NixOS, FreeBSD ports, OpenMandriva and Mageia already package it (`scripts/distro-survey.sh <pkg>` covers all of them in one call, plus read their actual `.spec`/`debian/rules`/`PKGBUILD`/ebuild/Void-template/Nix-derivation), **and** check for an existing `home:` project copy on OBS (`osc search --package <pkg>`).

Harvest from them: the **shared-library soname / subpackage split**, the `-devel`/`-tools`/`-doc` partitioning, build-system invocation and **build options** (`-D…`/`--enable-…`), `%check`/test wiring, any **required patches**, and the correct **SPDX license**.

Prefer basing the new package on the best existing reference — `osc copypac` from a good `home:` copy (see the copypac note), or port a distro's spec — then reconcile it against the cross-distro consensus, rather than writing from scratch and missing a subpackage split or a needed patch everyone else already carries. Treat a single distro's choices as one data point; where distros **disagree** (e.g. one ships only a static lib, another a versioned `.so`), follow openSUSE's Shared Library Policy and the majority of the distros that ship a proper shared lib. (Real case: cmark-gfm — new to Factory for mupdf's Markdown support; surveyed Fedora/Debian/Arch/etc. to settle the `libcmark-gfm`/`libcmark-gfm-extensions` soname subpackages + `-devel` split before packaging it in `Publishing`.)

## Submitting a brand-new package — go via the devel project, not straight to Factory

**When adding a NEW package, the destination depends on whether you are a *project-level* maintainer of its devel project.** For a package whose natural devel project you do **not** project-maintain (the common case — e.g. a new Python module belongs in `devel:languages:python`, a new library in `devel:libraries:c_c++`), the workflow is **two SRs in sequence**, not a direct submission to Factory:

1. **Stage the sources in your home project.** You can't create the package directly in a devel project you only hold *package-level* (not project-level) maintainership in — `osc meta pkg <devel-project> <newpkg>` returns **`403 Forbidden: You are not authorized to update this project`**. So create it in `home:<you>` instead (`osc meta pkg home:<you> <newpkg> -F meta.xml`, then `osc co home:<you> <newpkg>` from the osc working area, add the spec/`.changes`/sources, build, commit) — never `osc mkpac <prj> <pkg>`, which takes one argument inside a project checkout. → `references/osc-usage.md` "Package and checkout"
2. **`osc sr home:<you>/<newpkg> <devel-project>`** — submit the new package *to the devel project first*, so it gets **maintained there**. (Expect the `Warning: failed to fetch meta data … (new package?)` — normal for a new package.) The devel-project maintainers review/build/accept it.
3. **Only after it's accepted into the devel project**, submit from there to Factory: **`osc sr <devel-project>/<newpkg> openSUSE:Factory`** (a new-package submission — stricter `opensuse-review-team` legal/review pass).

Do **not** short-circuit by submitting `home:<you> → openSUSE:Factory` directly for a package that has an established devel project you don't project-own; the package should live in (and be maintained from) the proper devel project. (Real case: `python-siphash24` — staged in your `home:` project, SR'd to `devel:languages:python` first; the maintainer only held package-level rights there, so direct creation 403'd.) If you genuinely *are* the project-level maintainer of the target devel project, you can create + commit there directly and skip the home-project hop.

**Accept-and-forward (step 2→3, when you hold the rights).** If you *do* maintain the devel project (or the package within it) and are running the submission yourself, accept the home→devel SR with **`osc request accept <id> -m "…"`**. After accepting, osc detects that the package is developed for `openSUSE:Factory` and **interactively prompts** `… Forward this submit to it? ([y]/n)`. **There is no `--forward` flag on current osc** — it's that prompt — so in any non-interactive/scripted/agent context the prompt can't be answered and the forward is silently **aborted** (the accept still succeeds). Therefore the reliable two-step is: `osc request accept <id>` then **explicitly** `osc sr <devel-project> <pkg> openSUSE:Factory -m "…"` to file the devel→Factory SR yourself (it then goes through the normal `licensedigger`/`factory-auto`/`opensuse-review-team` chain). Confirm the accept landed by re-reading the devel spec `Version:` before forwarding. Without rights, you stop after filing the home→devel SR and leave the accept to the devel-project maintainers — never try to self-accept where you lack permission (it'll 403). (Real case: libbacktrace snapshot refresh — `osc request accept` landed it in `network:cryptocurrencies`, the forward prompt aborted under piping, so the Factory SR was filed with a plain `osc sr network:cryptocurrencies libbacktrace openSUSE:Factory`.) When the user has said they want to **maintain** the new packages, also add them to each package's `_meta` (`<person userid="<user>" role="maintainer"/>`, e.g. via `osc meta pkg <devel-project> <pkg> -e` or an API edit) and **say so in the SR message** so the devel-project reviewers expect the maintainer addition.

**When *someone else* accepts your home→devel SR, they usually forward it to Factory as part of accepting — check for an existing forward before filing your own (HARD RULE).** The interactive accept prompt `… Forward this submit to it? ([y]/n)` **defaults to yes**, so a devel-project maintainer who accepts your SR at the CLI routinely creates the devel→Factory SR too, under *their* name — a devel acceptance therefore normally *auto-forwards* to Factory without any action from you. If you then file your own `osc sr <devel-project> <pkg> openSUSE:Factory`, you create a **duplicate** competing in Factory staging, and osc tries to auto-supersede the existing one — which **403s** because it isn't yours (`created request id <new>` followed by `WARNING: could not change state of request <theirs>: HTTP Error 403: Forbidden`). So for any package accepted into its devel project by *another* maintainer, **before forwarding, check whether an open Factory request already exists**: `osc request list openSUSE:Factory <pkg> -s new,review` (or `osc api '/request?view=collection&project=openSUSE:Factory&package=<pkg>&states=new,review'`). If one is already there sourced from the devel project, **do not file another** — theirs already carries your change (an SR resolves its source at *accept* time, so the forwarded devel HEAD includes whatever was just accepted; confirm with the source `rev` in their request if unsure). Only forward yourself when *no* open Factory request exists (e.g. the accepter used a non-interactive/scripted accept where the prompt aborted — see the accept-and-forward note above). If you already filed a duplicate, **revoke yours** (`osc request revoke <your-id> -m "duplicate of <their-id>"`), never theirs. (Real case: python-torch cmake fix — accepted into `science:machinelearning` by another maintainer, who forwarded `s:ml/python-torch → openSUSE:Factory` as SR 1365345, already picked into `Factory:Staging:adi:40`; a follow-up `osc sr science:machinelearning python-torch openSUSE:Factory` created duplicate 1365356 and 403'd trying to supersede 1365345 → revoked 1365356.)

**NEVER accept or decline someone else's incoming request on your own initiative — HARD RULE, no exceptions, not even when you clearly hold the rights.** An incoming SR is another contributor's work landing in a project/package the user maintains; accepting it publishes their change under the user's maintainer authority, and declining it is a judgement about a colleague's work. Both are the user's call *every time*. Review it, summarise it, recommend accept or decline **with reasons — then stop and wait for an explicit instruction naming that request**. A prior "accept it" for one SR is not standing permission for the next one, and holding package-level maintainership is *not* the same as being authorised to use it unattended. This governs `osc request accept/decline/revoke` against any request the user did not create; it does **not** restrict the user's *own* submissions (filing, superseding and revoking those stays routine). See "Reviewing incoming requests" below for the review workflow that precedes the ask.

**Deleting a `home:`/scratch project REVOKES its open outgoing SRs — never delete a cone scratch project until the home→devel SRs are *accepted*.** An SR resolves its source at *accept* time, so `osc rdelete`-ing the source project while the SR is still `new`/`review` revokes it (and the updated content vanishes with the project — you'd redo the work). Once the home→devel SRs are **accepted**, the project is safe to delete: the follow-on **devel→Factory** SRs source from the *devel* project, not your home project, so they stay intact. (Real case: a fastmcp/bugzilla-mcp cone scratch project deleted while its 3 SRs were `new` revoked all three; redone, kept until accepted, then deleted with the Factory SRs untouched.)

- **Interdependent SRs (a new package that needs other in-flight SRs) — spell out the dependency in the submit message so staging co-stages them.** When you submit a package that cannot build until *other* open requests land (a new build-dep package, or a dependency whose SR adds a soname/lib the new package links), the staging manager has no way to know the ordering unless you tell them. List the related request ids explicitly in the `osc sr -m` message — e.g. a block like `INTERDEPENDENT REQUESTS - please stage together (will not build until these land): * sr#NNNN - <pkg> (build dep) * sr#MMMM - <pkg> (runtime)`. It's fine to submit the dependent package while its deps are still in review (a temporarily-red staging is expected); the note lets a human pull the whole set into one staging instead of bouncing it. (Real case: the falcosecurity-container-plugin SR depended on new plugin-sdk-cpp + a re-flex shared-lib SR + falco-libs; all four ids were listed in the submit message.)

**A version bump can introduce a NEW mandatory dependency that isn't in Factory yet — that blocks the update until the dep is packaged.** Before committing to an update, re-read the upstream dependency manifest (Python `pyproject.toml` `dependencies`/`requires-python`, `Cargo.toml`, CMake `find_package`, etc.) and check each *new* hard dependency exists in Factory (`osc develproject openSUSE:Factory <dep>` → 404 = absent; a `home:*:branches:*` hit is **not** "in Factory"). If a new mandatory dep is missing, the update is a **sequential/coordinated submission**: package the dependency into Factory first (via its devel project, per above), then submit the consumer once the dep lands. (Real case: `python-pytools` 2026.1.1 newly hard-required `siphash24>=1.6`, absent from Factory → had to package `python-siphash24` first; the pytools update parked until then.)
