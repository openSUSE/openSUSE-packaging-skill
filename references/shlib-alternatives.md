# Shared libraries and the `alts` framework

Owner of: the shlib subpackage/SONAME rules and the `libalternatives` (`alts`) conversion.

## Shared libraries

https://en.opensuse.org/openSUSE:Shared_library_packaging_policy

- A versioned shared library `libfoo.so.N[.x.y]` belongs in its own subpackage named `libfoo<N>` (or `libfoo-<VER>-<SONUM>` for the full form) with the SO version and dots-to-underscores encoded into the package name. Use `%package -n libfoo<N>` to set the name explicitly.
- The versioned shlib subpackage contains *only* the `.so.*` files (plus optionally the license in a versioned dir). Headers, `.so` symlinks, `.pc` files, `.la` files go in `-devel`.
- Avoid packaging static libraries; use `--disable-static`. Drop `.la` files unless the library lives outside `%_libdir`. **A version bump can *newly* start installing a static `lib*.a` that a prior release didn't** — it then surfaces as `error: Installed (but unpackaged) file(s) found: …/lib*.a` at the packaging stage (the compile/install succeed; rpm fails at the end). Fix by disabling the static build if CMake/configure offers a toggle, else `rm -f %{buildroot}%{_libdir}/lib*.a` in `%install`. (Real case: libcec 7.0.0→7.1.1 began installing `libcec.a`.) More generally, after any version bump re-check `%files` against what actually gets installed — bumps add/move/rename files (new static libs, relocated python bindings, new manpages) and the mismatch only shows up as unpackaged-files or a missing-file error at the very end of the build.
- If upstream ships an unversioned `libfoo.so`, patch the build to add a SONAME (e.g. `libfoo.so.suse0`) rather than packaging an unversioned shared library.
- **Use the `%ldconfig_scriptlets` macro for every shlib subpackage — never hand-write the ldconfig scriptlets. Apply this as part of default cleanup on any package you touch.** Replace `%post -n libfoo<N> -p /sbin/ldconfig` + `%postun -n libfoo<N> -p /sbin/ldconfig` (and any inline `/sbin/ldconfig` calls in `%post`/`%postun`) with a single `%ldconfig_scriptlets -n libfoo<N>`. The macro is the canonical openSUSE form and expands to the right `%post`/`%postun`; doing it by hand is stale style spec-cleaner won't fix for you. (When `%package -n` already matches `%{name}`, the bare `%ldconfig_scriptlets` form works too.)
- **On a version bump of a shared library, verify the SONAME/soversion from the *upstream source*, not by guessing — then bump the spec's `%define sover...` to match.** Don't assume "minor bump → soname unchanged" or "+1". Read the authoritative value from the build system: CMake `set(GDAL_SOVERSION 39)` / `SOVERSION` target property, autotools `-version-info`/`libtool` current:revision:age, or the produced `lib*.so.N`. (Real case: gdal 3.12→3.13 bumped `GDAL_SOVERSION` 38→39 in `gdal.cmake`; the spec's `%define soversion` was updated to 39 and the `libgdal38`→`libgdal39` subpackage rename followed.) A soname change then triggers the lib-subpackage rename **and** the `baselibs.conf` update below, and Factory staging will rebuild the library's consumer cone (expect a longer staging dwell).
- **HARD RULE — on a soname/lib-subpackage rename, also update `baselibs.conf`.** When a version/ABI bump renames the shlib subpackage (`libfoo1`→`libfoo2`, or full-version names like `libunrar7_2_5`→`libunrar7_2_6`), grep the package's `baselibs.conf` (often `Source99`) for the old library package name and update *every* occurrence to the new `%package -n` name. `baselibs.conf` hardcodes those names verbatim to generate the `-32bit`/`-64bit` baselibs packages; spec-cleaner and your spec edits don't touch it, so it silently goes stale and produces wrong/broken baselibs. (Real case: unrar 7.2.5→7.2.6 — `baselibs.conf` still said `libunrar7_2_5`.)
- **A major version that splits/renames a library can ship a *backward-compat* copy whose real SONAME differs from its filename — package it in the subpackage whose name matches the SONAME, or rpmlint's `shlib-policy-name-error` (badness 10000) aborts the build.** When upstream moves the implementation into a new library but keeps installing the old `lib<old>.so.N` name for source/link compatibility, that compat file often carries the *new* library's `DT_SONAME`. rpmlint's shared-library policy keys the **package name suffix off the SONAME version**, not the filename — so shipping `lib<old>.so.<N>` (SONAME `lib<new>.so.<M>`) in a `lib<old><N>` subpackage trips `shlib-policy-name-error … expected package suffix: <M>`. Fix by putting the compat file in the **`lib<new><M>`** subpackage (suffix matches the SONAME); its `.pc`/`-devel` symlink redirect to the new lib anyway. Check the real SONAME with `objdump -p <file> | grep SONAME` before assigning subpackages. Also: upstream may install that compat lib via `install(FILES …)` (non-executable, 0644 → rpmlint `shared-library-not-executable`) and create its symlinks via an `install(CODE …)` rule that ignores `DESTDIR` (so they never reach the buildroot) — fix the bit with a patch (`install(PROGRAMS …)`, upstreamable) and create the symlinks yourself in `%install`. (Real case: mbedtls 4.1.0 — crypto moved to TF-PSA-Crypto; `libmbedcrypto.so.4.1.0` has SONAME `libtfpsacrypto.so.2`, so the compat libs went into `libtfpsacrypto2`, not a `libmbedcrypto18` subpackage; `libeverest`/`libp256m` subpackages disappeared entirely.)
- **A project that ships many shared libs → one `lib<name><major>` subpackage *per soname*, even if upstream's own (Fedora/RHEL) spec dumps them all in the main package.** openSUSE shlib policy wants one subpackage per soname; it also keeps reverse-deps resolvable and upgrades clean (if the soname major is unchanged the subpackage name stays identical, so no Obsoletes churn). Read each soname from the install manifest (`lib<name>.so.<major>`). dlopened plugins/modules (non-versioned `.so` in a private dir) stay in main; the `.so` devel symlinks + headers go in `-devel`.
- **Under-linking is caught by openSUSE's `-Wl,-z,defs` (`--no-undefined`) and fails the build:** a library that *uses* symbols from another library but doesn't *link* it → `undefined reference to '<sym>'`. Fix by adding the missing link dependency (the build's `target_link_libraries` / `LIBS`). This is **upstreamable** — distros that don't enforce `-z,defs` (Fedora/RHEL/Ubuntu) resolve the symbols transitively at load time and never see the bug, so send the link fix upstream and cite the PR in the patch comment.
- **A consumer that `dlopen`s and fails with `undefined symbol: <3rd-party sym>` usually means a dependency is shipped *static-only* and built against *system* third-party libs.** A plugin/app that statically links `libfoo.a` inherits foo's *undefined* references to system codecs (libfoo.a only *references* `jpeg_*`/`opj_*`/`Brotli*`, it doesn't define them — openSUSE unbundles them to system libs), but the consumer's own link line never pulled those system libs in → the symbols are unresolved at `dlopen`. **Diagnose:** `ldd -r <consumer.so>` lists every undefined symbol; **split them** — the consumer's *own-API* symbols (e.g. `zathura_*`, resolved from the host executable at runtime — those are expected/harmless) vs the *third-party* ones (the real failure). Confirm with `nm <dep>.a | grep ' U '` (the static archive's undefined set) and `nm -D <syslib>.so | grep ' T '` to map each to its system lib. **First check bugzilla by the error string and survey distros** ([bugzilla-cve-triage](bugzilla-cve-triage.md), `scripts/distro-survey.sh`) — this kind of bug is often long-known with a ready fix (real case: zathura's `undefined symbol: jpeg_resync_to_restart` had a 6-year-old `boo#` with the Gentoo patch linked; Arch & Gentoo both carry a meson patch adding `-ljpeg -lopenjp2 -ljbig2dec`). **Two fixes:** (a) link the missing system libs explicitly in the consumer (meson `dependency('libjpeg')` etc.); (b) better — build the dependency as a **shared** library so its own `NEEDED` carries the codecs and every consumer just links `-lfoo`.
- **Converting an upstream *static-only* library to a shared library (openSUSE often ships `foo-devel-static` only):** build with the upstream shared toggle (`make shared=yes`, meson `default_library=shared`, CMake `-DBUILD_SHARED_LIBS=ON`). Gotchas seen on mupdf: ① if the upstream `install-shared-*` target *guards* on "no bundled thirdparty" (e.g. `USE_SYSTEM_LIBS=yes`) but you legitimately bundle some (a removed-from-Factory dep like gumbo), use the **generic `install` target** instead — it installs the shared lib without the guard. ② Pass the install mode so the `.so` is `0755`, else rpmlint `shared-library-not-executable` (mupdf: `SO_INSTALL_MODE=755`). ③ If upstream ships **no pkg-config file**, generate a `foo.pc` in `%install` (`Libs: -lfoo`, `Cflags: -I…`) so consumers' `dependency('foo')`/`pkgconfig(foo)` path works — that's what lets the consumer build *unpatched*. ④ Split into `lib<name><sover>` + `-devel` per the policy above; **don't** add `Provides/Obsoletes %{name}-devel-static` if the new `-devel` no longer ships the `.a` (it doesn't offer the matching feature). ⑤ Some libs (mupdf) set the `DT_SONAME` to the **full upstream version** (`libmupdf.so.27.2`), so the soname — and thus the `lib<name>27_2` subpackage name — **churns every release**; flag this trade-off (smaller consumers + auto-rebuild on CVE vs a rename each bump). The dependency and its sole consumer form a **coupled soname bump**: submit both Factory SRs cross-referenced ("stage together"), since the old consumer breaks the moment the new lib lands. (Real case: mupdf static→shared `libmupdf27_2` + `mupdf.pc`, fixing zathura-plugin-pdf-mupdf `boo#1165273`; verified by installing both RPMs in a container and seeing `zathura --version` list the plugin instead of the symbol error.)

- **HARD RULE — if the package ships a shared library, run `scripts/soname-check.sh` on the built RPMs: a versioned symlink whose name is *not* the SONAME is a cross-version file conflict.** rpmlint and `source_validator` both pass such a package, because the defect is invisible with only one version installed; it detonates in the target project's staging when the old and new library packages both claim the same version-independent path, and comes back as a reviewer decline. A `%files` glob like `%{_libdir}/libfoo.so.*` is the usual way it gets in. **Drop such links in `%install`** rather than narrowing the glob, so the next bump cannot reintroduce them. (Real case: mupdf shipped `libmupdf.so.28` beside SONAME `libmupdf.so.28.1`, and `libmupdf28_0` conflicted with `libmupdf28_1` on `/usr/lib64/libmupdf.so.28`.) The script also flags a bare unversioned `lib*.so` in a runtime package and advises when a package name does not encode its SONAME version — see `scripts/README.md` "`soname-check.sh`".

## Alternatives — Factory default is `libalternatives` (`alts`)

https://en.opensuse.org/openSUSE:Packaging_multiple_version_guidelines

openSUSE Factory's default for a generic binary name (`/usr/bin/NAME` shared across flavours or implementations) is **`libalternatives`** (`alts`), not Debian's `update-alternatives` symlink-farm-plus-scriptlets. libalternatives is declarative: the package ships a config file, and *nothing runs at install time*. New packages use it; existing `update-alternatives` users are converted when touched.

**HARD RULE — convert `update-alternatives` to `libalternatives` when you encounter it.** Any spec you edit, clean, or review that still uses `update-alternatives` is converted as part of that touch — not a follow-up, not "only if the user asked". Same class of on-sight conversion as dropping `Group:` and converting a hand-rolled npm vendor tarball to the `node_modules` service. Tells: `Requires(post): update-alternatives` / `Requires(postun): update-alternatives`; `%post`/`%postun` calling `update-alternatives` or `%python_install_alternative` / `%python_uninstall_alternative` with no `%bcond_without libalternatives` path; `%ghost %{_sysconfdir}/alternatives/` entries. The `.changes` bullet is `- Switch from update-alternatives to libalternatives` (or a `*` under the session's cleanup/update dash). The one exception is the shared-command-pair sequencing HARD RULE below: converting only one side of a pair that still shares a generic name creates an installcheck conflict — convert both sides (or wait for the other maintainer) before landing yours.

**The whole mechanism, in two file kinds:**

- `%{_datadir}/libalternatives/<generic-name>/<priority>.conf` — a plain key=value file. Highest priority wins by default; the user overrides with `alts -n <generic-name>`.
- `%{_bindir}/<generic-name>` — a **plain symlink to `alts`** (relative, literally `alts`), shipped as a regular file in `%files`. `alts` reads the configs at *run* time and `exec`s the winner.

Keys, all verified against shipped packages (`vim`, `python3NN-docutils`, `dbus-launch`):

```
binary=%{_bindir}/rexx-%{name}     # required — the real implementation
man=regina.1                       # optional — man page the generic name resolves to
group=rexx,rxqueue                 # optional — switch these names together
options=KeepArgv0                  # optional — pass argv[0] through
```

**Consequences worth knowing, because they are what make it better:**

- **No `%post`/`%postun`, no `Requires(post)`, no `/etc/alternatives`, no install-time state at all.** Delete all of that when migrating. `Requires: alts` (and `BuildRequires: alts`) is the only runtime dep.
- **Python singlespec packages have macros — use them; do not hand-write the `.conf`.** `%bcond_without libalternatives` (Factory default ON); `%python_clone -a` already emits the conf when the bcond is on; `%python_group_libalternatives NAME [NAME…]` groups names so they switch together (`%python_group_libalternatives` is a no-op unless `%{with libalternatives}`); `%python_libalternatives_reset_alternative NAME` in `%pre` migrates an installed update-alternatives user. Keep `%python_alternative %{_bindir}/NAME` in `%files`. Recipe: `references/language-packaging.md` "Console scripts". Reference users: Factory `python-uv`, `python-ruff`.
- **Non-Python packages have no rpm macros.** Write the `.conf` yourself in `%install` (a `cat > … <<EOF` heredoc is the idiomatic form) and list both the conf and the symlink in `%files`.
- **`group=` only takes effect if *every* member declares an identical group.** A group named on one side only is **silently inert** — so a cross-package group (two implementations of the same command set) requires the *other* package to migrate too, and to declare the same list. Never name a member no provider can supply.
- **Two providers of the same generic name coexist cleanly** — they own different `<priority>.conf` paths, and the shared `%{_bindir}` symlink and directories are byte-identical, so rpm sees no conflict.
- **SLE-15 / Leap 15 still lack `alts`.** If the devel project still builds those targets (`osc repos`), keep a dual path: `%if 0%{?suse_version} > 1500` / `%bcond_without libalternatives` / `%else` / `%bcond_with libalternatives` (Factory `python-mutmut`) and keep the `%post`/`%postun` `%python_install_alternative` fallback. For a Factory-only package, drop `%post`/`%postun` and `Requires(post): update-alternatives` entirely (Factory `python-uv` / `python-ruff`).

**HARD RULE — when two packages provide the same command, `rpm --test` does NOT prove they can coexist.** rpm **skips `%ghost` entries in conflict detection**, so an `update-alternatives` pair (whose `/usr/bin/<name>` and `/etc/alternatives/<name>` are `%ghost`) passes a local `rpm --test` install and *still* gets declined by Factory's **installcheck**, which compares the built file lists directly:

```
found conflict of Regina-REXX-3.9.7 with ooRexx-5.1.0
  /etc/alternatives/rexx    [mode mismatch: g -644 vs g -755]
  /usr/bin/rexx             [l777 vs g l777]
```

Verify by **downloading the other package and diffing file lists**, not by test-installing:

```
osc getbinaries openSUSE:Factory <other-pkg> standard x86_64
rpm -qp --qf '[%{FILENAMES}\t%{FILEMODES:perms}\t%{FILEFLAGS:fflags}\n]' <rpm> | LC_ALL=C sort
```

then `join` the two sorted lists and confirm every shared path matches on **mode *and* flags**. (`LC_ALL=C` matters — a locale-default `sort` silently breaks `join`.)

**HARD RULE — migrating ONE side of a shared-command pair CREATES a conflict; both sides must land, and the other one has to reach the target FIRST.** libalternatives ships `%{_bindir}/<name>` as a **real** symlink to `alts`, whereas update-alternatives `%ghost`s that same path. So the moment you migrate, your package's file list stops matching the un-migrated provider's, and installcheck rejects the pair on a **real-vs-ghost flag mismatch** — a conflict that did *not* exist while both sides were on update-alternatives:

```
found conflict of Regina-REXX-3.9.7-1.2.x86_64 with ooRexx-5.2.0-1.3.x86_64
  /usr/bin/rexx    [mode mismatch: l777 root:root -> alts, g l777 root:root]
  /usr/bin/rxqueue [mode mismatch: l777 root:root -> alts, g l777 root:root]
```

(`-> alts` = your real symlink; the bare `g l777` = their ghost.) installcheck compares your candidate against **what is in the target now**, not against your other pending request — so the sequencing is forced: the *other* package's migration must be accepted **into the target project** before yours can pass, and a migration SR of yours sitting in a devel project does not count. Plan the order before you migrate anything: if the other package is not yours, that is a wait on its maintainers plus a Factory acceptance, and your own request will be declined in the meantime. Migrating both sides is still the durable fix — it removes the modes from the picture entirely — but it is a coordinated two-package landing, exactly like a coupled soname bump. (Real case: Regina-REXX vs ooRexx — an earlier revival, SR 1287670, was declined for exactly the conflict above; both packages moved to libalternatives with a shared `group=rexx,rxqueue`.)
