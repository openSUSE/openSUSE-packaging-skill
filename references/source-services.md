# Source services (`_service` / tar_scm / obs_scm)

Owner of: service modes and what each one means for what you run and what you commit, tagless
upstreams, and the switch back to a release tarball.

## Updating a package that uses a source service (`_service` / tar_scm)

Some packages carry a `_service` (and a `_servicedata`) instead of a hand-managed tarball — the source archive is regenerated by OBS source services (`tar_scm`/`obs_scm`, `set_version`, `recompress`, …). Whether you run them, and with which command, is decided entirely by each service's `mode=` — see "Service modes decide what you run AND what you commit" below before touching anything. For these, **a version bump is a `_service` edit + a service run, not a manual tarball swap**:

1. **Bump the revision in `_service`.** Change the `<param name="revision">` (e.g. `v0.9.5` → `v0.9.15`). That tag/branch/commit is what gets exported. (Always verify the new tag is genuinely newer — see "Checking for newer upstream versions"; tag *dates*, not string order.)
2. **Run the services locally with `osc service run` — never `runall`.** `osc service run` honours the declared modes and is the correct default; add `osc service mr` (manualrun) when the package's fetch services are `mode="manual"`, which is what a locally-driven tar_scm/obs_scm bump normally uses. The run re-clones/fetches, exports the new revision to a fresh tarball, `set_version` rewrites `Version:` in the spec, `recompress` produces the configured compression, and `_servicedata`'s `changesrevision` advances to the new commit. See "Service modes decide what you run AND what you commit" below — `runall` is mode-blind and will happily fire `mode="buildtime"` services that are meant to run on the worker, leaving you with an artifact you must not commit.
3. **Verify it actually moved.** `tar_scm` can print a benign `merge: origin/<tag> - not something we can merge / Already up to date` and still be wrong if a stale cache wasn't refreshed — so confirm: `_servicedata` `changesrevision` changed, the new tarball's top-dir is `<name>-<newversion>/`, and the version string inside the sources matches. Then `osc rm` the old tarball and `osc add` the new one.
4. **Remove the leftover clone cache.** A local run of a `tar_scm` git service leaves a working git checkout dir (`<pkg>/`) in the package directory. `osc status` does **not** list it (it's untracked and osc-ignored), so it won't be committed — but `rm -rf <pkg>` it anyway to avoid confusion and stray disk use.
5. **`changesgenerate` produces a raw git-log dump — always curate it.** When `_service` has `<param name="changesgenerate">enable`, the run prepends a `.changes` entry containing **every git commit subject** between the old and new `changesrevision`. Across a multi-version jump that is 50+ one-line bullets — which violates the changelog guideline ("summarise for an openSUSE *user*, ~10–15 lines with ~20 the ceiling — abridge with a closing sub-bullet, never cutting a CVE line — don't dump upstream's log"). Keep the service-stamped date/author header, then **replace the bullet dump with a curated user-facing summary** (new default behaviour, new platform/toolchain support, notable fixes) before committing. Real case: kcbench 0.9.5→0.9.15 generated ~60 bullets; collapsed to ~14 lines.

After the service run, the rest is normal: `spec-cleaner`, local `osc build`, the source validator, then commit. On commit, the `_service`/`_servicedata` changes and the new tarball go up together; the locally-run (`manual`) services do **not** re-run server-side.

### Service modes decide what you run AND what you commit — HARD RULE

`osc service` has one subcommand per mode, and picking the wrong one silently
produces files that must not be checked in. **`osc service run` is the norm** —
it honours each service's declared `mode=`, which is the entire point of the
modes:

| command | runs services with mode |
|---|---|
| `osc service run` (`r`) | `trylocal`, `localonly`, or no mode set — **the default**; takes an optional service name |
| `osc service manualrun` (`mr`) | `manual` — "a human runs this locally, on demand" |
| `osc service precommit` | exactly what a commit would run |
| `osc service remoterun` (`rr`) | nothing locally — triggers the run server-side |
| `osc service localrun` (`lr`) | as `run`, plus `serveronly` — osc's own help files this under *"not for common usage anymore"* |
| `osc service disabledrun` (`dr`) | `disabled` — legacy, same *"not for common usage anymore"* note |
| `osc service runall` (`ra`) | **every service, ignoring mode entirely — anti-pattern, never use it** |

**Anti-pattern: `osc service runall`.** It is mode-blind: it runs
`mode="buildtime"` services too, and those exist precisely because they are
supposed to run on the OBS worker during the build, never in your checkout.
Anywhere you are tempted to reach for `runall`, the right command is
`osc service run` (plus `osc service mr` when the package's services are
`mode="manual"`).

**Do not author `mode="disabled"` in a new or updated `_service`.** Semantically
"disabled" means *this service must not run at all*. The mode for "a service a
human runs locally on demand" is **`mode="manual"`**, driven with
**`osc service mr`**. Historically people wrote `disabled` where they meant
`manual`, so plenty of existing packages carry it as a legacy artefact.

**When you meet an existing `mode="disabled"`, do not blindly convert it and do
not blindly run it — investigate which of the two cases it is:**

- **Legacy leftover** — `disabled` used the way `manual` is used today → convert
  to `mode="manual"` (`osc service mr`) as part of the cleanup, and say so in the
  `.changes`.
- **Genuinely meant to stay disabled** — the service must not run (kept only for
  documentation/history, or running it would fetch/overwrite something
  undesirable) → leave it completely alone.

Evidence for telling them apart: does the package's committed content look like
the service's output (i.e. someone has clearly been running it by hand)? does
`.changes`/the package history mention running it? would running it actually
regenerate what is committed? **If you cannot determine it confidently, leave it
alone and flag it to the user** rather than guessing.

The rule for `tar` / `compress` / `recompress` specifically:

- **`mode="buildtime"` → do NOT run them locally.** The worker regenerates the
  tarball at build time. Commit the **`.obscpio`** (plus `.obsinfo`, `_service`,
  `_servicedata`) and **no tarball**.
- **`mode="manual"` (or a local mode) → you MUST run them,** because nothing
  else will. Commit the resulting **`.tar.?z`** and **not** the `.obscpio`.
  This is mostly the git/LFS-backed packages.

**Never commit both.** Reviewers decline it — *"please pick .obscpio or tarball,
we don't need both"* (see `references/submit-watch.md`, reviewer-feedback list).
The failure mode is exactly this: a blind `runall` on a package whose `tar`
service is `buildtime` materialises a `.tar.xz` next to the `.obscpio` that was
already tracked, both get added, and the SR carries two source mechanisms for
one source. (Real case: SR 1369815.)

**This is why the validator gate is `osc service run source_validator`** — never
`runall source_validator`, which on a service-bearing package fires the other
services as a side effect and hands you exactly the artefact you must not
commit. The direct-binary form is equivalent —
`/usr/lib/obs/service/source_validator --outdir <tmpdir>` — and is also the
workaround when `osc service` fails outright on a git/scmsync checkout with
``The `apiurl` argument of `makeurl()` must not be empty``. Check its real exit
code, unpiped, as always.

**Before committing after any service run, look at what actually changed** —
`osc status` — and confirm you are adding exactly one source artifact for the
source. An unexpected `.tar.*` appearing beside a tracked `.obscpio` (or vice
versa) means you ran the wrong mode, not that the package needs both.

**A rolling `nightly` (or other non-release) tag breaks `@PARENT_TAG@` versioning — restrict tag matching with `match-tag`.** For a service that tracks a *branch* (`<param name="revision">main</param>`) with `<param name="versionformat">@PARENT_TAG@+@TAG_OFFSET@</param>`, `git describe` picks the **most recent tag reachable from HEAD**. If upstream adds a moving tag *on* the HEAD commit (e.g. a `nightly` tag that CI re-points every build), `@PARENT_TAG@` resolves to `nightly` and `@TAG_OFFSET@` to `0`, producing a bogus version like `nightly+0` — which is a **downgrade** versus the previous `1.0.1+196` (rpm vercmp ranks the digit-leading string newer than the alpha-leading one) and breaks the update. Fix by telling the service to consider only release tags: add **`<param name="match-tag">v*</param>`** (it passes `--match 'v*'` to `git describe`), so the version goes back to `1.0.1+<offset>`. Also confirms why a snapshot's parent tag may be an *older* release than the latest tag — the higher `vX` tag simply isn't on the tracked branch's ancestry. (Real case: neovim-gtk — upstream's new `nightly` tag on `main` HEAD produced `nightly+0`; `match-tag=v*` restored `1.0.1+279`.)

### Tagless upstream (no tags, no releases, not on PyPI) — pinned-commit `obs_scm`

Some upstreams never cut a release in any form: zero git tags, zero forge releases, nothing on PyPI (real case: NVIDIA/skillspector). Two rules:

- **Never ship a locally-built sdist/tarball whose version exists nowhere upstream.** factory-auto runs a download check against every `Source:` URL; a `files.pythonhosted.org` (or any) URL that 404s is an automatic decline ("Source URLs are not valid"), and a hand-built tarball has no verifiable provenance even if the URL were served. (Real decline: skillspector "2.3.10" — a locally-built sdist one patch-version past upstream's static 2.3.9, submitted with a phantom PyPI URL.)
- **The fix is a pinned-commit `obs_scm` snapshot** — `scripts/scm-snapshot.sh <pkg> <url> <sha>` scaffolds and verifies it: version `X.Y.Z~gitYYYYMMDD.<hash8>` where `X.Y.Z` is upstream's own declared version (pyproject/CMake), committed `.obscpio` so nothing needs downloading at review time. Two traps it already encodes, for when you hand-write the `_service`: `%h` in `versionformat` abbreviates to **7** chars — pin an explicit `<param name="version">` if you want 8; and verify the produced `.obsinfo` version string before committing.
- **Python + static pyproject version → the dist-info keeps the RELEASE version, not your snapshot `%{version}`.** hatchling/setuptools emit `<name>-<pyproject-version>.dist-info` (e.g. `skillspector-2.3.9.dist-info`) while the RPM version is `2.3.9~git…`, so `%{python_sitelib}/<name>-%{version}.dist-info` in `%files` no longer matches and the build dies on unpackaged files. Hardcode the upstream version's dist-info path with a comment flagging it for the next bump.

### Prefer a real release tarball over the service when one exists

**When a `_service` tracks a git *tag* and upstream publishes that same released tag as a tarball, prefer switching to the upstream tarball directly and dropping the whole service machinery.** A real release tarball is simpler, verifiable, and avoids the git-clone/repack churn — the service adds no value once a proper released tarball exists for the same revision. This commonly comes up when a package was put on a git-snapshot scheme (`X.Y.Z+git.%cd`) during a period when upstream wasn't tagging, and upstream has since resumed cutting releases.

Mechanics:
1. Set `Source0:` to the upstream tarball URL (full HTTPS), and update `Version:` to the release.
2. `osc rm _service _servicedata *.obscpio *.obsinfo` (drop the whole service set), then `osc add <name>-<version>.tar.*`.
3. Build, validate, commit as usual.

**Caveats:**
- This applies only to a *released* tarball matching the tracked tag. If the package **deliberately tracks unreleased git snapshots ahead of the last tag** (a documented reason to be ahead of upstream's releases), keep the service — see "Checking for newer upstream versions". Confirm the snapshot scheme isn't intentional before ripping it out.
- A snapshot→release switch can change the **version string** and (for libraries) often coincides with a **soname bump** — recheck `%define sover` against the new `version-info`/`SONAME` and update the lib subpackage name *and* `baselibs.conf` (see "Shared libraries"). Re-check `%files` too: a release can add/rename/move installed files (a new binary, a relocated header) that a snapshot didn't, surfacing as `Installed (but unpackaged) file(s) found` at the end of the build.

### After switching to a tarball, recheck whether `autoconf`/`automake` are still needed

For an **autotools** package, whether you still need `autoconf`/`automake`/`libtool` + an `autoreconf` step depends on **which kind of tarball** you switched to — verify, don't assume either way:

- A **GitHub/GitLab git auto-archive** (`/archive/refs/tags/<tag>.tar.gz`) is a raw git snapshot: it ships only `configure.ac`/`Makefile.am` (and often `autogen.sh`), **no** generated `configure`/`Makefile.in`/`aclocal.m4`. So `autoreconf` *is* required → keep `autoconf`/`automake`/`libtool`. (When no release *asset* exists for the tag — `gh api …/releases/tags/<tag>` 404s, or the assets list is empty — the auto-archive is your only option.)
- A **real `make dist` release tarball** (a maintainer-uploaded release asset) ships a pre-generated `./configure` — so `autoreconf` and the autoconf/automake/libtool BuildRequires can be **dropped**.

**Check:** extract the tarball and `ls configure Makefile.in aclocal.m4`. `configure` present → drop the regen tooling; absent (only `configure.ac`/`autogen.sh`) → keep it. (Real case: libiscsi 1.20.3 — no release asset, so the tag archive lacked `configure`; autoconf/automake/libtool and the `autoreconf -fiv` were kept. nbd 3.27.1 — same situation, autoreconf added in `%build`.) Run the regen in whichever phase the spec already uses (`%prep` is typical; `%build` before `%configure` is also fine). Note that this distinction also means **the SR's `factory-auto` download check still verifies the auto-archive URL** — that's fetchable on a standard GitHub port, so it passes.
